# 02｜R0～R15、局部变量、寄存器溢出与恢复

## 1. Cortex-M4 的核心寄存器

| 寄存器 | 典型职责 | 异常切换时的基本处理 |
|---|---|---|
| R0～R3 | 参数、返回值、计算中间量 | 硬件自动压入基本异常栈帧 |
| R4～R11 | 按 AAPCS 通常需跨函数调用保留的通用寄存器 | PendSV 软件保存和恢复 |
| R12 | 临时寄存器（IP） | 硬件自动保存 |
| R13 / SP | 当前活跃的栈指针（MSP 或 PSP） | PSP 关联到任务的 TCB |
| R14 / LR | 普通函数返回地址；Handler 内可为 EXC_RETURN | 原任务 LR 硬件压栈；Handler 的 EXC_RETURN 软件保存 |
| R15 / PC | 指令执行位置 | 硬件自动压栈与恢复 |
| xPSR | 程序状态 | 硬件自动保存 |

> R9 在 AAPCS 中可能用作平台寄存器，具体用途取决于 ABI；**FreeRTOS 仍在 PendSV 中按 R4～R11 完整保存**。

## 2. 局部变量到底放在哪里？

```c
void task(void *arg) {
    uint32_t count = 10;
    uint32_t sum = 20;
    for (;;) { count++; sum += count; }
}
```

编译器可能使 `count` 对应 R4、`sum` 对应 R5；也可能把它们安排在栈中，或者因优化而重排、消除。**不存在运行时全局“变量名 → 固定寄存器编号”的表**。编译器在每一个指令位置都知道要访问哪些寄存器、栈槽、固定内存地址；调试信息可能记录变化的位置，但 RTOS 不需要这份信息。

若寄存器不够，编译器可使用栈槽进行 **register spilling（寄存器溢出/换出）**，如 `STR R0, [SP, #8]`、`LDR R0, [SP, #8]`（仅示意）。局部变量也可能因取地址、数组、对齐或 ABI 等原因置于栈中。

### 为什么切换时不逐个保存局部变量？

1. 处于寄存器中的仍有意义的值：通过保存寄存器现场保留。
2. 处于任务栈中的数据：RAM 内容原本就保留，无需逐字复制。
3. 全局/静态变量：位于共享的内存区域，不属于每任务独占现场；多个任务访问时需要同步。
4. 通过动态分配得到的内存：仍在内存中；RTOS 切换不迁移这块内存。
5. 已被优化删除或不再活跃的值：无需恢复。

### “R4～R11 会不会占满？”

会占用，但只有 8 个物理寄存器不等于只能有 8 个局部变量。CPU 在任意时刻只需保存**当前仍有价值的执行状态**，编译器会复用寄存器并把必要数据放在栈中。

## 3. 为什么恢复时“知道哪个是哪个”？

CPU 不认识变量 `count`；它执行机器指令，例如：

```asm
ADDS R4, R4, #1     ; 编译器决定这里用 R4
ADDS R5, R5, R4     ; 编译器决定这里用 R5
```

切换前 `STMDB R0!, {R4-R11,R14}` 将 R4 数值保存在“R4 槽”，R5 数值保存在“R5 槽”；恢复时 `LDMIA R0!, {R4-R11,R14}` 把对应位置读回原寄存器。**PC 也恢复成原指令位置**，因此后续机器指令依然访问同一编号的寄存器，不用做变量名查找。

## 4. 异常处理程序里为什么能拿 R2 临时存 TCB 地址？

发生 PendSV 的最初，硬件已经把**被切出任务的 R2 原值**压入该任务 PSP 栈帧。因此 Handler 可以把活跃的 R2 当工作寄存器；这不会丢失任务原值。随后 `BL vTaskSwitchContext` 按 ABI 可以改变 Handler 正在使用的 R2——但 Handler 根本不再依赖这个临时值。

**两层含义必须区分**：

- “任务 R2 的原值”已在 PSP 异常栈帧保存。
- “Handler R2 暂时指向 Task1_TCB”只是临时指针，用完即可丢弃。

## 5. 如何实际知道编译器把变量放在哪？

在 Keil/CubeIDE：低优化等级（先 `-O0`）、防止函数被内联、查看 Disassembly 和 Registers，并与调试器变量视图核对；再切换到 `-O2` 对比。对于某个确定的汇编地址，才能准确说明当时变量具体的位置。观察示例见 [08-实验与调试](08-实验与调试.md)。
