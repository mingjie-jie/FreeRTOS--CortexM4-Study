# 02｜寄存器彻底讲透：R0～R15、调用约定、变量、现场恢复

> **必读主线**：谁决定 `count` 在 R4？R4 如果被占满怎么办？任务切换时为什么保存 R4～R11、不保存 Handler 的 R2？恢复时 CPU 凭什么知道哪个变量对应哪个寄存器？
>
> 本章针对 **STM32F407 / ARM Cortex-M4F / AAPCS / 常见非 MPU FreeRTOS 移植**。示意汇编不是某个 C 文件的真实反汇编；真实映射依赖编译器、优化级别与具体指令位置。

## 0. 先分清四个层次

| 层次 | 它知道什么 | 它不需要知道什么 |
|---|---|---|
| C 程序员 | `count`、`sum`、函数、作用域 | 每一条机器指令的实际寄存器分配 |
| 编译器/链接器 | 哪条指令使用 R4、哪一处 `[SP,#12]` 保存变量、函数入口位置 | RTOS 下次调度哪个任务 |
| CPU 硬件 | 寄存器编号、内存地址、机器指令、异常机制 | C 变量名、任务名字 |
| FreeRTOS | 如何保存任务寄存器和独立栈、哪个 TCB 可运行 | `count` 是否叫 count、其值在 R4 还是 SRAM |

**最重要的原则：保存和恢复的是“按寄存器编号、按栈地址排列的机器状态”，不是“变量名”。**

## 1. R0～R15 的逐个作用与常见场景

Cortex-M4 的 R0～R12 是通用寄存器；R13～R15 有专门含义。**R4～R11 不是任务私有寄存器**：只有一套 CPU 物理寄存器，任务切换时使用各自栈保存副本。

| 寄存器 | AAPCS / CPU 约定 | C 代码中的常见用途 | 在基本异常中的保存方式 |
|---|---|---|---|
| **R0** | 参数 1；32 位普通返回值 | `func(a,...)` 第 1 个参数，运算临时量 | **硬件自动压栈** |
| **R1** | 参数 2；部分双寄存器返回值 | 第 2 个参数、中间值 | 硬件自动压栈 |
| **R2** | 参数 3 | 第 3 个参数、中间值；PendSV 里临时放旧 TCB 地址 | 硬件自动压栈 |
| **R3** | 参数 4 | 第 4 个参数；PendSV 里临时存 `&pxCurrentTCB` | 硬件自动压栈 |
| **R4** | 被调用者保存 | 需要跨函数调用长期保持的活跃值 | PendSV 软件保存 |
| **R5** | 被调用者保存 | 同上 | PendSV 软件保存 |
| **R6** | 被调用者保存 | 同上 | PendSV 软件保存 |
| **R7** | 被调用者保存 | 有些编译配置可用作帧指针 | PendSV 软件保存 |
| **R8** | 被调用者保存 | 通用长生命周期数据 | PendSV 软件保存 |
| **R9** | 平台寄存器或被调用者保存，取决于 ABI | 静态基址/线程寄存器/通用值等 | 移植代码统一随 R4～R11 保存 |
| **R10** | 被调用者保存 | 通用值 | PendSV 软件保存 |
| **R11** | 被调用者保存 | 有时用作帧指针 | PendSV 软件保存 |
| **R12（IP）** | 过程内临时寄存器，允许被调用者改写 | 编译器、链接器生成的临时计算/跳板 | 硬件自动压栈 |
| **R13（SP）** | 当前可见栈指针 | 当前函数的栈帧、`PUSH/POP` | 任务使用的 PSP 值经 TCB 管理 |
| **R14（LR）** | `BL` 链接寄存器 | 通常保存函数返回位置；Handler 中可保存 EXC_RETURN | **任务原 LR** 由硬件压栈；**Handler LR/EXC_RETURN** 由移植层保存 |
| **R15（PC）** | 程序计数器 | 指令执行位置、分支目标 | 硬件自动压栈/异常返回恢复 |

> “被调用者保存（callee-saved）”不是“寄存器永远不变”：被调用函数可以使用 R4～R11，但正常返回前必须恢复调用者可观察到的原值。R9 有平台例外，实际需要匹配目标 ABI。

### 1.1 R0～R3：参数传递是怎么发生的？

```c
__attribute__((noinline))
int add3(int a, int b, int c) { return a + b + c; }

int result = add3(10, 20, 30);
```

典型思路（**示意**）：

```asm
MOVS R0, #10         ; 参数 a
MOVS R1, #20         ; 参数 b
MOVS R2, #30         ; 参数 c
BL   add3            ; LR = 返回地址；PC 跳到 add3
; 返回后 R0 存放结果 60
```

少量整数/指针参数通常走 R0～R3；更多参数以及不适合放寄存器的内容由 ABI 规定通过栈等方式传递。**不要将“所有 float 参数都走 R0～R3”当成通则**：硬浮点 ABI 还涉及 S 寄存器，详见第 5 节。

### 1.2 R4～R11：跨函数调用的值为什么适合留在这里？

假设函数需要在调用另一个函数后继续使用 `sum`：

```c
uint32_t sum = 100;
external_function();
sum += 2;
```

编译器可能把 `sum` 放在 R4，因为 `external_function()` 按调用约定必须保护 R4 的值；也可能放在栈中。若此函数本身写了 R4，那么它自己的入口/出口也需要按 ABI 保存恢复上一级调用者的 R4。

### 1.3 R12：IP 不代表“固定存放某个变量”

R12 是调用者保存的临时寄存器；链接器生成分支桩（veneer）等场景也可能使用它。它在异常入栈的八个基本寄存器之中，不需要 PendSV 单独保存。

### 1.4 R13：为什么 SP、PSP、MSP 有三个名字？

- R13 / SP：普通指令使用的**当前选中的**栈指针视图。
- MSP、PSP：Cortex-M 内核内真实存在的两套栈指针。
- Thread Mode 通常可通过 CONTROL.SPSEL 使用 MSP 或 PSP；**Handler Mode 始终使用 MSP**。
- 被中断的任务通常使用 PSP。硬件将任务的 R0/R1/R2/R3/R12/旧 LR/PC/xPSR 保存到**任务 PSP 栈**，PendSV 在 Handler Mode 使用 MSP。

因此同一时刻 `MRS R0,PSP` 与 `MOV R0,SP` **可能得到不同的地址**！后者在 PendSV 中读到的是 MSP。

### 1.5 R14：**三个容易混淆的“返回地址”**

1. **普通函数调用的 LR**：例如执行 `BL foo`，LR 是调用点后面的返回位置（Thumb 状态标记也需遵守约定）。
2. **任务被中断前的 LR**：进入 PendSV 时，硬件把任务的原 LR 放入它自己的基本异常栈帧中，位置是 `[basic_frame+0x14]`。
3. **异常处理程序当前的 R14**：硬件在进入 Handler 后将其设为 EXC_RETURN，如 `0xFFFFFFFD`。在你的 ARMCC PendSV 里，`STMDB R0!,{R4-R11,R14}` 存的是**这一份 EXC_RETURN**，不是第 2 种 LR。

恢复时先 `LDMIA ... R14` 得到新任务 EXC_RETURN；`BX R14` 触发异常返回；硬件最后再把新任务的原 LR 从它的栈帧恢复。**同一个 R14 在不同阶段有不同含义**。

### 1.6 R15：PC 如何前进？

- 正常顺序执行时，CPU 沿机器指令流前进；Thumb 指令可能占 16 或 32 bit，不是永远加 4。
- `B` 修改控制流，`BL` 修改控制流并设置 LR，`BX LR` 在普通函数中返回。
- 读 PC 的某些 Thumb 指令中，会观察到与当前指令地址存在流水线相关偏移，不应机械地把调试器所有 PC 数值都理解为“当前 C 代码行地址”。
- FreeRTOS 首次启动时，`pxPortInitialiseStack` 预填入入口函数 PC；后续任务恢复时，PC 是硬件异常入栈时保留下来的返回位置。

## 2. AAPCS 调用约定和 RTOS 切换是两套规则

**普通 `BL` 调用 C 函数**：

| 分类 | 寄存器 | 由谁保证保存？ |
|---|---|---|
| 调用者保存（caller-saved） | R0～R3、R12（LR 也会被 `BL` 改写） | 调用者若需要旧值，要自行保护 |
| 被调用者保存（callee-saved） | R4～R8、R10～R11，R9 按平台约定 | 被调用者返回前恢复 |
| 栈对齐 | 公共函数调用边界通常要求 SP 8 字节对齐 | 由编译器和底层汇编共同保证 |

**异步任务抢占**：可能发生在任意机器指令边界，**此时没有可依赖的“函数刚好返回”时机**。硬件保存 R0～R3、R12、旧 LR、PC、xPSR；PendSV 额外保存 R4～R11、EXC_RETURN，保证切出去的任务能“继续执行”。

结论：**保存 R4～R11 不是因为编译器只把局部变量放在这里；而是因为硬件基本异常栈帧没有替 RTOS 保存这些通用寄存器。**

## 3. 局部变量到底能放在哪？

以 `Task1()` 中的 `count` 为例，有以下情况：

| 编译器策略 | `count` 可能在哪里 | 切换时怎么办 |
|---|---|---|
| 寄存器分配 | R4/R5/R0 等当前可用寄存器 | 寄存器按编号保存、恢复 |
| 放入栈槽 | `[SP, #offset]`，任务栈 SRAM | 数据本来就留在任务栈；只需保证恢复原任务的栈及基址寄存器 |
| 保存到某个对象 | `struct`、动态对象、全局/静态地址 | 不需要“在切换时复制”；共享对象要考虑并发同步 |
| 寄存器复用 | 不同生命周期的变量先后共享同一个 R4 | 只保存中断点那一瞬间的真实 R4 状态 |
| 常量传播、优化删除 | 甚至没有物理存储槽 | 不需要恢复不存在的活跃数据 |

**重要：C 自动局部变量的“名称”不等于特定存储槽；即使名为 `count`，在不同 PC 地址处也可能位于不同地方。**

### 3.1 变量超过 8 个怎么办？Register spilling

编译器可以安排变量到 SRAM 栈槽，典型模式：

```asm
STR R0, [SP,#12]  ; 写回某个栈槽（偏移只是示意）
...
LDR R0, [SP,#12]  ; 再读入寄存器
```

叫 **寄存器换出/溢出（register spill）**。不能理解成 CPU 真的“有额外隐形寄存器”；是普通 `LDR/STR` 访问 RAM。

一个任务可以同时有几十、几百个变量（受 RAM、栈空间、优化、数据结构大小等限制），但 CPU 物理寄存器永远只有这些。每个任务自己的 PSP 栈保持局部栈槽内容；切换不遍历所有 C 变量。

### 3.2 “为什么变量没有被保存但恢复后还在？”

例如 `count` 位于地址 `0x200020A0` 的 Task1 栈槽：

```text
Task1 正在运行：RAM[0x200020A0] = 1234
切换到 Task2： Task2 不会重用 Task1 的独立栈内存
切回 Task1：  恢复它的 PSP 和相关基址寄存器，再读同一地址仍为 1234
```

**栈里不需要复制一遍所有局部变量**。需要复制到新的低地址栈区的，是 CPU 中还没有落在任务栈里的寄存器现场。

### 3.3 `volatile` 能决定寄存器分配吗？

`volatile` 限制编译器对对象访问的优化（每个必要访问仍要遵守语义），**不等于线程安全、原子性或自动互斥**。要在两个 FreeRTOS 任务间安全共享计数/状态，还需要根据场景使用原子操作、临界区、队列、任务通知或互斥量。

## 4. “它怎么知道哪个数据恢复到哪个寄存器？”

从 C 看：

```c
uint32_t count = 10;
uint32_t sum = 20;
count++;
sum += count;
```

编译器可能在某一段生成（**仅示意**）：

```asm
MOVS R4, #10
MOVS R5, #20
ADDS R4, R4, #1
ADDS R5, R5, R4
```

一次任务切换前若 R4=11、R5=31：

```asm
STMDB R0!, {R4-R11,R14}   ; 保存每个寄存器的数值到规定槽位
...
LDMIA R0!, {R4-R11,R14}   ; 从规定槽位恢复到同号寄存器
```

切回后 R4 仍为 11、R5 仍为 31，原来的 PC 又指向下一条预定机器指令，CPU 就继续使用 R4/R5。它根本不需要把变量名 `count` 编码到任务 TCB 里。

**寄存器存储槽位置是指令集规定的：** `STMDB` 的列表按寄存器编号排列，最低编号寄存器写在最低地址；`LDMIA` 同样按编号从低到高恢复。具体地址公式详见 [07-地址演算](07-栈地址计算演练.md) 和 [13-完整栈帧](13-寄存器现场与异常栈帧详图.md)。

## 5. FPU 的 S0～S31 又是什么？

STM32F407 有单精度浮点单元（Cortex-M4F），另外有 S0～S31、FPSCR 等状态。

| 部分 | 典型作用 | Cortex-M4F FreeRTOS 切换 |
|---|---|---|
| S0～S15、FPSCR（及预留槽） | 浮点运算/参数/结果等，具体受 hard-float ABI 约束 | 扩展异常栈帧由 Cortex-M 硬件负责（可能 lazy stacking） |
| S16～S31 | 需跨函数调用保留的高位浮点寄存器 | `TST R14,#0x10` 判断后由 PendSV `VSTMDBEQ/VLDMIAEQ` 保存恢复 |
| CONTROL.FPCA | 浮点上下文活动状态 | 影响异常入栈是否需要扩展浮点帧 |
| EXC_RETURN.bit4 | 返回栈帧格式 | 1=基本帧；0=扩展浮点帧 |

**注意**：有硬件 FPU 但未使用浮点上下文，不意味着每次都需要保存 S0～S31；与工具链 `-mfloat-abi=soft/softfp/hard`（或 ARMCC 对应选项）、具体代码及浮点活动状态有关。

## 6. 专项解疑：PendSV 为什么把 R2 用完就不保存？

源码：

```asm
LDR R3, =pxCurrentTCB    ; R3 = &pxCurrentTCB
LDR R2, [R3]             ; R2 = &OldTCB
...
STR R0, [R2]             ; OldTCB.pxTopOfStack = 保存后的栈顶
STMDB SP!, {R0,R3}       ; Handler MSP 保存临时现场，并保持对齐
BL vTaskSwitchContext    ; 更新 pxCurrentTCB
LDMIA SP!, {R0,R3}
LDR R1, [R3]             ; R1 = &NewTCB
LDR R0, [R1]             ; R0 = NewTCB.pxTopOfStack
```

这里要分清**两个完全不同的 R2 内容**：

1. **Task1 本来的 R2**：异常入口硬件已经将其保存到 Task1 PSP 的**基本异常栈帧**中，等 Task1 恢复时自动取回。
2. **Handler 临时给 R2 放的 `&OldTCB`**：只是为了执行 `STR R0,[R2]`；用完无须再用。`BL vTaskSwitchContext()` 按 AAPCS 可以覆盖当前 Handler 的 R2，没关系。

为什么只跨 `BL` 保存 R3？因为它持有**`pxCurrentTCB` 变量所在内存位置**，后面要用它解引用新 TCB。`R0` 与 `R3` 成对压入 MSP 共 8 字节，兼顾对齐；R0 之后立即被新的栈顶覆盖。

> 精确地说：不是“R2 不会丢”，而是“**任务原 R2 已保存，Handler 临时 R2 即使被覆盖也不需要保留**”。

## 7. 怎么实测“变量 → 寄存器”位置？

1. 在 Keil MDK 打开 `View → Disassembly Window`、Registers、Memory、Call Stack。先用关闭优化/`-O0`，之后切换到 `-O2`。
2. 对某个确定 **PC 位置**，结合 `MOV/ADD/LDR/STR/PUSH/POP`、`SP` 和内存视图分析，不要只看 C 源代码行。
3. 对 `noinline` 的有参函数重点观察 R0～R3 和返回时的 R0。
4. 对长生命周期的局部变量观察 R4～R11 和栈槽；用实际反汇编结论为准。
5. 在 FreeRTOS 的 PendSV 中观察 R2 原值与异常栈帧中保存的 R2 槽位是否一致（从 PSP 基本帧偏移 `+0x08` 读取；有浮点扩展帧时需先找到基本帧起点）。
6. 参考 [12-寄存器分配实验](12-寄存器分配与反汇编实验.md)、[08-调试](08-实验与调试.md)。

## 8. 六句高频复习答案

1. **R0～R3 主要是参数/临时寄存器**；任务被中断的原值硬件自动保存。
2. **R4～R11 需由 FreeRTOS 补充保存**，因为基本异常栈帧里没有它们。
3. **SP 有 MSP/PSP 两套硬件寄存器**，Handler 用 MSP；任务通常用 PSP。
4. **LR 在任务与 Handler 有不同含义**；EXC_RETURN 控制异常返回方式。
5. **PC 是机器指令执行位置**；第一次运行从人工初始栈帧恢复入口 PC，后续从上次异常栈帧恢复。
6. **FreeRTOS 不知道变量名字、不需要知道**；它只需要恢复寄存器编号、任务栈和 PC。
