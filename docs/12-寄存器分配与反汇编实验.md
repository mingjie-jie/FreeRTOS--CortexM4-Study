# 12｜Keil 实验：亲眼看见变量、R0～R15 和函数调用

> 目标：不凭猜测，而是通过 **Disassembly + Registers + Memory + Call Stack** 确认某条 C 语句对应哪些机器指令、局部变量此刻在哪个寄存器或栈槽中。

## 一、先准备工程

- 芯片：STM32F407 / Cortex-M4F。
- 工具：Keil MDK（你之前提供的 `__asm void` 是 ARM Compiler 5 风格）。
- 在已有 STM32 项目中加入 [`examples/stm32_register_lab/task_register_lab.c`](../examples/stm32_register_lab/task_register_lab.c)。
- 关闭或降低优化，便于看到直接、容易理解的指令；为了观察不同优化策略，可以分别使用低优化、较高优化进行对比。
- 函数 `noinline`、`volatile` 等写法只为控制教学实验可观测性，不代表通常应在真实项目中强制这样写。

## 二、实验 1：R0～R3 怎么传参数？

```c
__attribute__((noinline))
uint32_t FourArgs(uint32_t a, uint32_t b,
                  uint32_t c, uint32_t d)
{
    return a + b + c + d;
}

volatile uint32_t g_result;

void Test(void)
{
    g_result = FourArgs(1, 2, 3, 4);
}
```

**观察点**：在 `BL FourArgs` 前暂停，查看 R0/R1/R2/R3。常见 ABI 情况分别是 1、2、3、4；进入函数后可能立即入栈或者再分配给其他寄存器。单步到返回附近，查看 R0 通常是 10。

**不要误解**：不是说 `a` 的一生都必须在 R0；它只需在符合 ABI 的函数调用边界按规定传递。

## 三、实验 2：为什么保存 LR？函数嵌套有什么影响？

```c
__attribute__((noinline)) uint32_t Add2(uint32_t x) { return x + 2; }
__attribute__((noinline)) uint32_t TwiceAdd(uint32_t x)
{
    uint32_t first = Add2(x);
    return Add2(first);
}
```

1. 在调用 `TwiceAdd` 处找到 `BL/BLX`，记下 LR。
2. 进入 `TwiceAdd`，观察类似 `PUSH {...,LR}` 的函数序言（最终形式依编译器而定）。
3. 进入 `Add2`，新的 `BL` 会改写 LR。
4. `TwiceAdd` 返回前，编译器必须让**上一层调用点的返回位置**保持正确；它可以使用栈或其他符合 ABI 的办法。

问：**若 `BL` 总是覆盖 LR，为何嵌套函数仍能层层返回？** 因为每一层都依调用约定保护自己的返回信息。普通函数返回时可能使用 `BX LR` 或 `POP {...,PC}`。

## 四、实验 3：R4～R11 真的存局部变量吗？

```c
__attribute__((noinline))
uint32_t SumWithCall(uint32_t seed)
{
    uint32_t sum = seed;
    for (uint32_t i = 0; i < 6; ++i)
    {
        sum += Add2(i);
    }
    return sum;
}
```

你希望跨 `Add2()` 调用保留 `sum` 或循环索引 `i`，编译器常会：

- 把它们放在需要被调用者保留的 R4～R11 中；
- 或放入自己分配的栈槽中；
- 或改变循环形式和变量生命周期，生成与你想象不同的代码。

**方法不是靠源代码数变量个数来推断，而是找到每一条 `ADD/LDR/STR/MOV` 对应的寄存器和栈偏移。**

可以建立你自己的观察表：

| 机器地址（自己填） | 反汇编指令 | R4 值 | SP 值 | 变量位置判断 |
|---|---|---|---|---|
| `0x0800....` | `MOV ...` | ... | ... | ... |
| `0x0800....` | `BL Add2` | ... | ... | ... |
| `0x0800....` | `LDR ...` | ... | ... | ... |

## 五、实验 4：变量多于寄存器怎么办？

下面示例故意用数组制造 RAM 对象；与编译器的寄存器溢出优化不是同一回事，但能看到**栈空间是如何分配并通过地址访问的**。

```c
__attribute__((noinline))
uint32_t StackArray(uint32_t seed)
{
    volatile uint32_t values[12];
    for (uint32_t i = 0; i < 12; ++i) values[i] = seed + i;
    uint32_t sum = 0;
    for (uint32_t i = 0; i < 12; ++i) sum += values[i];
    return sum;
}
```

观察 `SUB SP,SP,#...`（或者对应其他栈分配指令）及 `[SP,#offset]`。在 Memory 窗口输入当前 SP，检查数据变化。**数组的连续存放不等于 spill；真正的 register spill 是编译器把原本可能驻留寄存器的活跃值临时存入栈槽。**

## 六、实验 5：FreeRTOS 切换时任务自己的 R2 到哪里去了？

在实际已可稳定运行的 FreeRTOS 工程里：

1. 在 `xPortPendSVHandler` 的 `MRS R0,PSP` 之后观察 PSP：指向旧任务硬件基本栈帧；**不要立即把异常处理程序当前 R2 当成任务的原 R2**。
2. 若任务采用基本栈帧：`*(uint32_t *)(PSP+8)` 是旧任务 R2 的保存槽；`*(uint32_t *)(PSP+0x18)` 是旧任务恢复 PC 槽。
3. 再单步到 `LDR R2,[R3]`，此时 Handler 的 R2 变成 `&OldTCB`；这并**没有覆盖栈中保存的 Task1 原 R2**。
4. 调度到其他任务后，Handler 的 R2 可以被 C 调度器修改；其原临时值不需要保留。
5. 下次切回 Task1，硬件异常返回时，会从 Task1 的栈恢复它自己的 R2 值。

> 如果 EXC_RETURN.bit4=0，PSP 指向的是**扩展浮点异常栈帧**，上述偏移不能直接套用；先找到其中基本帧的起点。也要留意 xPSR 中的栈对齐标记。

## 七、实验 6：PC 为何能够自动恢复？

查看人工初始化任务栈的 `pxPortInitialiseStack`：任务函数指针写入 **PC 槽**。首次 SVC 启动时，执行 `MSR PSP,R0` + `BX R14`，进入任务入口。后续 PendSV 恢复的是上一次保存的指令继续地址。

**断点注意**：在异常入口/出口单步、通过 DAP 调试等操作可能影响对异常发生顺序的直觉；以向量表、PSP/MSP、EXC_RETURN 和 Memory 快照联合判断。
