# 16｜一次看完：xTaskCreate → SVC → PendSV → osDelay → 再恢复

> 这是一张把前 15 章串起来的“总线图”。目标不是背函数名字，而是弄清每个阶段 **PC、PSP、MSP、TCB、寄存器** 由谁维护。

## 1. 应用创建任务

```c
xTaskCreate(Task1, "Task1", 256, NULL, 2, &handle1);
xTaskCreate(Task2, "Task2", 256, NULL, 1, &handle2);
vTaskStartScheduler();
```

源码任务创建链会分配/绑定 TCB 与任务栈，并调用移植层 `pxPortInitialiseStack()` 构造**人工初始执行现场**：任务参数在 R0 槽，入口地址在 PC 槽，xPSR.T=1，EXC_RETURN 设成适当返回模式。TCB 的 `pxTopOfStack` 记录这份栈帧起始位置。

任务创建并不会直接执行任务函数；编译器生成的 `BL Task1` 不参与普通的 `xTaskCreate()` 到首次运行过程。

## 2. 启动第一个任务：prvStartFirstTask + SVC

```text
main(Thread/MSP) → vTaskStartScheduler → xPortStartScheduler
    → prvStartFirstTask
       ├─ 读 VTOR 再读向量表第 0 项 → 恢复初始 MSP
       ├─ CONTROL 清理、打开必要异常、DSB/ISB
       └─ SVC 0
          └─ 异常硬件入栈（启动流的现场在 MSP）
             → vPortSVCHandler(Handler/MSP)
                ├─ 从 pxCurrentTCB 获取任务初始栈顶
                ├─ LDMIA 恢复 R4-R11 与 EXC_RETURN
                ├─ MSR PSP,R0
                └─ BX EXC_RETURN
                    └─ 从 PSP 人工基本帧恢复 PC = Task1 入口
```

这里 **没有旧的 RTOS 任务需要保存**，因此 SVC Handler 与 PendSV 处理路径不同。

## 3. Task1 已运行：CPU 执行真实机器指令

编译器可能让 `count` 在 R4，另一个数组在 Task1 栈内；如果用了函数调用，按 AAPCS 使用 R0～R3 传参，LR 保存返回地址。这些都是普通 Cortex-M 机制，与 RTOS 是否存在无关。

Task1 运行期间：

```text
模式 = Thread Mode
CPU 当前使用 PSP = Task1 任务栈
PC = Task1 或 Task1 调用的函数里某条指令地址
TCB1.pxTopOfStack = 上次保存时的地址（并非实时 PSP 的同步镜像）
```

**特别重要**：任务真正执行时，PSP 会随函数调用/局部栈分配变化，TCB 里的 `pxTopOfStack` 不要求每条指令都实时更新。只有进入上下文切换过程，移植层才把保存后的 PSP 栈顶写回 TCB。

## 4. Task1 调用 osDelay（假设 1000 Tick）

CMSIS 层最终进入 FreeRTOS `vTaskDelay()`；内核记录唤醒时间并把当前任务从就绪路径转为阻塞。随后请求任务切换。中断优先级条件满足时 PendSV 开始运行：

```text
Task1(Thread/PSP1)
   → PendSV 异常进入
       → 硬件把 Task1 R0-R3、R12、原 LR、PC、xPSR 压在 PSP1
       → Handler 使用 MSP
       → PendSV 软件把 Task1 R4-R11、EXC_RETURN（及需要时 S16-S31）压 PSP1
       → TCB1.pxTopOfStack = 保存后的地址
       → vTaskSwitchContext() 选择下一个 READY TCB
       → 从 TCB2 恢复寄存器，设置 PSP2
       → BX EXC_RETURN：硬件恢复 Task2 PC 等
```

任务阻塞后，从调度器角度不再具备被选中的资格；但它的栈和所有活跃内存状态仍留在 RAM，**不是任务被销毁**。

## 5. 系统 Tick 到期后

`xPortSysTickHandler()` 调用 `xTaskIncrementTick()`，更新 Tick、检查延时列表；到期任务从阻塞链路转为 READY，必要时请求 PendSV。只要 Task1 再次被选为运行任务，就从 TCB1 指向的栈恢复上下文。

它通常先回到 `vTaskDelay` 的一条后续指令，然后完成 `vTaskDelay`、`osDelay` 的正常返回，最后才运行应用中 `osDelay(1000)` 的下一行代码。**PC 恢复的是机器指令的继续点，不是新调用一次 Task1()**。

## 6. 一张总表：每一个重要变量到底在哪？

| 对象 | 任务正在运行时 | PendSV 保存旧任务之后 | 新任务恢复时 |
|---|---|---|---|
| PC | CPU 当前任务机器指令位置 | 旧 PC 留在旧任务硬件帧 | 新 PC 从新任务硬件帧恢复 |
| R0～R3、R12 | CPU 物理寄存器 | 旧值由硬件保存在 PSP 栈 | 由硬件从新 PSP 栈恢复 |
| R4～R11 | CPU 物理寄存器 | PendSV 软件保存在旧 PSP 栈 | 软件 `LDMIA` 恢复 |
| R14（原任务 LR） | 函数返回地址 | 由硬件保存在旧任务基本帧 | 异常返回时硬件恢复新任务的原 LR |
| Handler R14 | 不存在这个阶段 | EXC_RETURN 被软件保存 | 软件恢复后 `BX R14` |
| PSP | 当前正在运行任务的栈指针 | 通过 TCB 记录保存现场栈顶 | `MSR PSP,...` 指向新任务硬件帧 |
| MSP | 不参与任务正常运行 | Handler 栈、C 调度调用临时保存 | 任务恢复后留给下一次 Handler |
| `pxCurrentTCB` | 指向当前 TCB | `vTaskSwitchContext` 改为新 TCB | 保持指向被选中的 TCB |
| 自动局部变量 | 部分寄存器、部分 PSP 栈槽 | 寄存器入栈，原有栈槽内容不需要搬运 | 原寄存器值和栈槽仍可访问 |

## 7. 你真正需要会回答的五个问题

1. **任务第一次运行时 PC 从何而来？** 任务创建时将入口函数地址写入人工初始异常帧。
2. **从哪里知道当前应该恢复哪个任务？** 调度器更新 `pxCurrentTCB`，再找到对应 TCB 首成员 `pxTopOfStack`。
3. **为什么 `BL vTaskSwitchContext` 本身不会直接切换任务执行点？** 它只是普通函数调用，返回到 PendSV 后继续恢复新 PSP，真正的任务 PC 在异常返回时才改变。
4. **任务局部变量保存在哪？** 由编译器决定，可能在寄存器或任务栈；RTOS 不关心变量名。
5. **阻塞 1000 Tick 就必须恰好在 Tick+1000 执行吗？** 不是，到期只是 READY，是否运行受优先级等条件影响。
